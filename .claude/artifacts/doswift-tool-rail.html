DoSwift · 悬浮工具入口

工具轨与状态手柄

抛开现有菜单形式，重新问一遍：这个工具入口应该长什么样。结论是它不该是一个菜单——菜单是阅读型 UI，而调试工具需要的是识别型 UI，而且它要同时容纳两类根本不同的东西。

三句话概括。把「计量型」工具（FPS、内存、网络活动）从菜单里拆出去做成常驻读数；把「任务型」工具（层级检查、沙盒、抓包）从居中的列表换成贴边的竖向工具轨；浮窗手柄从「蓝圆套白圆」升级成承载状态的入口——图标表示当前工具，颜色表示是否在跑。全程不碰屏幕中心，也不再有模态遮罩。

先拆开：这是两类东西

现有菜单把它们塞进同一个列表，这是分类错误，也是它总让人觉得「少了点什么」的根源。

计量型 gauge

你要的是持续看着它。没有「打开」和「关闭」这两个动作——关掉就没意义了。它应该一直待在角落，数字在跳。

FPS内存CPU网络活动视图层数
现在藏在菜单里 — 无法理解，你没法「打开 FPS 看一眼再关掉」
应该常驻的窄读数 — HUD 药丸，可拖拽、记住位置、默认关闭

任务型 task

你要的是进入 → 用完 → 退出。一次一个，占满屏幕，专注做完。层级检查器就是这一类。

层级检查沙盒抓包日志
现在菜单二级项 — 形态勉强可用，但加上去就变成点三次
应该全屏 / sheet，入口是工具轨，一层扁平，不需要二级

四种状态并排

同一份工具集，四种时刻。注意手柄在四张图里始终是同一个人格——空闲时淡，有事时亮，不突然换个性格。

要诚实说的是：菜单是瞬时的，收起时占屏为 0；工具轨在交互期间常驻。所以这不是「谁更小」的简单账，而是——菜单每次操作都遮 14.4% 且压在正中，一天开几十次；新形态最坏情况遮 5.9%、全程贴边，中心区一次都没碰。

考虑过但排除的

这几个都是认真想过的替代方案，排除理由都是具体的。

方案为什么不用
摇一摇唤起不可发现——没人猜得到；和其他库的摇一摇处理器冲突；调试时手已经在屏幕上，摇手机是纯额外动作。
边缘滑出抽屉和 iOS 系统返回手势正面冲突，屏幕左右各 20pt 是系统保留区，抢不过来。
底部 sheet模态。你会没法一边开着工具一边操作被调试的 app——而这恰恰是调试的常态。
径向 / 环形菜单中文标签在弧线上放不下，iOS 上也没有先例。圆环好看，但读不了。
干脆去掉浮窗需要它可拖拽（避开内容）且永远可达，这两点只有浮窗能同时满足。

这个方案的弱点

不藏。下面四条是真的代价，不是可以说过去的。

图标识别度有上限

无文字图标永远有歧义。所以保留 10pt 小标签，不做纯图标轨——但小标签在中文下可读性本身就一般。

给别人演示时不可预测

「单击进上次的工具」对不熟悉的人会意外。靠手柄图标自解释来缓解，但这是真实代价。

要给每个工具做图标

顺带说，这件事本来就要做：现在 DoSwiftMenuItem 里全是 UIImage(systemName:) 占位，HierarchyInfoView 里还挂着 5 个 TODO: Use actual asset。

改动量比改菜单大

要动 DriftView 的拖拽语义、新增工具轨视图、把计量型工具从菜单里拆出去。不是一天的活。

落地顺序

每一步都能单独编译验证，符合这个仓库现有的「每批完成后由你手动编译」节奏。

  1. 先做手柄，砍掉菜单

    DriftView 的图标从「蓝圆套白圆」换成真实工具图标（准星 + 状态点），同时把 DoSwiftMenuViewController 从 DoSwiftCore 的菜单里摘掉。这一步先验证：去掉菜单之后，手柄单独存在是否成立。

  2. 再做工具轨

    新增贴边竖轨视图，长按手柄就地展开。这一版让它只承载「任务型」四项，不碰计量型。

  3. 把计量型拆出去

    新增 HUD 药丸组件（可拖拽、吸附、记住位置、默认关闭），把 FPS / 内存这类读数从列表里搬过来。

  4. 回填 hasSubMenu 那条线

    工具轨是扁平结构，DoSwiftMenuItem 的子菜单能力、chevron 渲染、maxVisibleItems 都应该整套删掉——它们是为旧形态存在的。
